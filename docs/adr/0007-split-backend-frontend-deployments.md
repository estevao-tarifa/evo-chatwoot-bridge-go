# ADR-0007 — Split deployments: backend binary image, frontend nginx image

- Status: Accepted
- Date: 2026-10-10
- Related: ADR-0001 (CORS), ADR-0006 (cookies)

## Context

The legacy backend is a Node process that (in the Manus scaffolding) also
served/bundled frontend assets — backend and frontend were one artifact. The
rewrite mandates the opposite: the frontend is **never a runtime dependency of
the backend** (`AGENTS.md` §8) and both are deployed independently (plan §5).
Deployment target: `deploy/docker-compose.prod.yml` with two services (bridge,
frontend) plus the existing MySQL; CI is per component (`paths:` filters).

## Decision

1. **Backend image**: multi-stage build (`golang:1.27` → scratch or
   distroless-static). Static binary, **non-root**, CA certificates copied,
   timezone data embedded via `import _ "time/tzdata"` (ADR-0003 — no tzdata
   files in the image). No shell, no package manager, no frontend files.
   Healthcheck via the binary itself (`bridge healthcheck` subcommand hitting
   `/healthz`), since scratch has no curl/wget.
2. **Frontend image**: nginx (alpine), serving the Vite build output with SPA
   fallback, cache headers and gzip. **Only static assets** — no Node at
   runtime.
3. **The backend never serves frontend assets**: no `//go:embed` of the SPA,
   no static file server, no HTML responses. Enforced by review (this line is
   the reference for rejecting such PRs).
4. **API base URL is configured at runtime**, not baked at build time: the
   frontend image contains a small `config.js` (`window.__BRIDGE_CONFIG__`)
   generated by the image entrypoint / mounted config, so one image works
   against any backend. (Alternative “rebuild per environment” rejected to
   keep one immutable frontend artifact.)
5. **CORS/credentials**: when the frontend origin differs from the backend
   origin, the backend allows exactly `CORS_ALLOWED_ORIGINS` with credentials
   (ADR-0001) and the session cookie uses `SameSite=None; Secure` (ADR-0006).
   The recommended production topology is nevertheless a single reverse proxy
   (nginx) fronting both (`/` → frontend image, `/api` → bridge) — same-origin,
   simpler cookies, TLS in one place. The images stay independent either way.
6. **CI per component**: `.github/workflows/backend.yml` (`gofmt -l`, `go vet`,
   `staticcheck`, `go test ./...`, migration fixture test, image build) gated by
   `paths: [backend/**]`; `.github/workflows/frontend.yml` (`tsc`, lint, build,
   image build) gated by `paths: [frontend/**]`. Deploy workflow consumes
   tagged images independently: `backend/vX.Y.Z`, `frontend/vX.Y.Z`.
7. `deploy/docker-compose.prod.yml`: two services + external MySQL; restart
   policies; explicit `CORS_ALLOWED_ORIGINS`; no dependency link between the
   two services (frontend may be down without affecting the bridge; the deploy
   gate explicitly tests stopping the frontend mid-traffic).

## Consequences

- (+) Backend image is a few MB, starts in <100 ms, has no Node/CVE surface;
  frontend can be cached/CDN’d independently.
- (+) Independent rollouts: a frontend rollback never touches the bridge
  process and vice versa.
- (−) Two artifacts to version and monitor; the operator must keep CORS/cookie
  config consistent with the chosen topology (compose example ships with both
  variants documented).
- Risk: LOW — main footgun is CORS/`SameSite` misconfiguration, caught by the
  explicit “frontend works remotely + backend survives frontend stop”
  gate and the docker-compose example.

## Alternatives

- **Single image (backend serves SPA)** — rejected: recreates the coupling the
  mission removes; complicates the Go binary with asset concerns.
- **Static frontend on a CDN / object storage** — compatible with this design
  (the SPA is just files), no decision needed now; nginx image is the shipped
  default because it works offline/on-prem.
- **Server-side rendering** — out of scope; the SPA is preserved as-is.
